## 문제

여러 지역에 걸쳐 주문·상품·고객·창고·배송을 관리하는 가상의 리테일 회사에서 일한다고 상상해 봅시다. 데이터는 여러 시스템에 살고 있습니다.

- **Eventhouse**에는 주문·배송·수요 신호 같은 실시간 트랜잭션 데이터가 저장됩니다.
- **Lakehouse**에는 상품 카탈로그·고객 프로필·예측 같은 차원 데이터가 있습니다.

전통적 접근에서는 분석가가 _어느_ 시스템에 _어느_ 데이터가 있고 어떻게 조인하는지를 알아야 합니다. **"남서 지역에서 반품을 유발한 프로모션은 무엇인가?"** 같은 하나의 질문은 반품 → 상품 → 프로모션 → 지역으로 순회해야 하는데, 이 과정에서 두 시스템과 여러 테이블을 넘나들어야 합니다.

## 왜 온톨로지인가?

온톨로지는 원시 데이터 위에 **시맨틱 계층**을 만들어 이 문제를 해결합니다.

| 온톨로지 없이 | 온톨로지와 함께 |
|---|---|
| 분석가는 테이블 이름과 조인 컬럼을 알아야 함 | 비즈니스 사용자는 자연어로 질문 |
| `cust_lt_val` 같은 컬럼 이름은 모호 | *Customer lifetime value* 같은 속성이 자기 설명적 |
| 시스템 간 질의는 수동 오케스트레이션 필요 | 온톨로지가 개념을 소스에 투명하게 매핑 |
| 새 데이터 소스 추가는 질의 재작성 | 새 바인딩 추가는 질의를 깨지 않고 모델을 확장 |

## 무엇을 만들까

다음 여섯 단계에 걸쳐 **리테일 공급망 온톨로지**를 15개 엔티티 타입과 18개 관계로 점진적으로 구축합니다.

1. **핵심 상거래** — Customer, Order, Product
2. **주문 상세 & 카테고리** — OrderLine, ProductCategory
3. **지리** — Region, Store
4. **이행 & 물류** — Shipment, Carrier, Warehouse
5. **재고 & 수요** — Inventory, Forecast, DemandSignal
6. **완성 모델** — Promotion, Return

각 단계는 새로운 개념을 도입하고 성장하는 그래프를 보여 줍니다. 끝날 즈음에는 Microsoft Fabric IQ에서 그래프 질의, GQL, 자연어 데이터 에이전트 상호작용을 뒷받침할 수 있는 완전히 연결된 온톨로지를 갖게 됩니다.

## 다룰 핵심 개념

- **엔티티 타입**과 **식별자 속성** — 구성 요소들
- **관계**와 **카디널리티** — 엔티티가 어떻게 연결되는지
- **연결 엔티티** — OrderLine으로 Order와 Product를 잇기
- **지리 계층** — Region → Store 모델링
- **크로스 소스 통합** — 하나의 엔티티, 여러 데이터 소스
- **그래프 순회** — 복잡한 질문에 답하기 위해 연결을 따라가기

어떤 상거래 시스템에서도 가장 기본적인 세 개의 엔티티부터 시작합시다.
