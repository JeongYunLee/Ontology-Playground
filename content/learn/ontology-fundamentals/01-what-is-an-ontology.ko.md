## 그래프로 사고하기

커피숍을 설명한다고 상상해 보세요. **사물**(매장, 상품, 고객, 주문)과 그 사이의 **연결**을 이야기하게 됩니다. 고객이 주문을 *하고*, 주문에는 상품이 *포함*되며, 매장은 상품을 *비치*합니다.

**온톨로지**란 바로 그것을 형식적으로 기술하는 방식입니다. 어떤 도메인에 어떤 유형의 사물이 있고, 그것들이 서로 어떻게 관련되는지 정의하는 것이죠. 데이터 자체가 아니라 데이터의 *모양*을 그린 청사진에 가깝습니다.

## 엔티티, 속성, 관계

모든 온톨로지는 세 가지 구성 요소로 지어집니다.

| 개념 | 의미 | 예시 |
|---------|--------------|---------|
| **엔티티 타입 (Entity type)** | 사물의 범주 | `Customer`, `Product`, `Store` |
| **속성 (Property)** | 엔티티에 관한 사실 | `Customer.name`, `Product.price` |
| **관계 (Relationship)** | 엔티티 사이의 연결 | `Customer → places → Order` |

속성에는 **타입**(문자, 숫자, 날짜, 불리언)이 있고, 모든 엔티티에는 각 인스턴스를 유일하게 구분해 주는 **식별자 속성**(예: 고객 ID)이 최소 하나는 있어야 합니다.

## 온톨로지가 중요한 이유

온톨로지 없이 데이터는 그저 테이블과 컬럼일 뿐입니다. 온톨로지가 있으면 시스템은 "매출"이 `Store.city`로 그룹화한 `Order.totalAmount`의 합이라는 사실을 이해할 수 있습니다. 왜냐하면 온톨로지가 그 개념들이 어떻게 연결되는지 알려 주기 때문이죠.

이것이 **시맨틱 데이터 모델**의 기반입니다. SQL을 직접 손으로 쓰는 대신, 원하는 것을 자연어로 기술하면 시스템이 온톨로지를 사용해 올바른 쿼리를 생성합니다.

## 개념에서 코드로

온톨로지는 보통 **RDF/OWL**로 표현됩니다. RDF/OWL은 클래스, 속성, 관계를 기술하기 위한 XML 기반 표준이에요. 하지만 XML을 손으로 직접 작성할 필요는 없습니다. [온톨로지 디자이너](#/designer) 같은 도구로 시각적으로 만들고 유효한 RDF로 내보낼 수 있습니다.

## 핵심 정리

- 온톨로지는 어떤 도메인의 **사물 유형**과 **그것들이 어떻게 관련되는지**를 정의합니다
- 데이터가 아닌 스키마이며, 내용이 아닌 모양을 기술합니다
- 시맨틱 쿼리를 가능하게 합니다: 자연어로 질문하면 구조화된 답을 얻을 수 있습니다
- 표준 포맷은 **RDF/OWL**이지만 JSON 형태로도 다룰 수 있습니다

```quiz
Q: 다음 중 온톨로지의 구성 요소가 아닌 것은?
- 엔티티 타입
- 속성
- SQL 쿼리 [correct]
- 관계
> 온톨로지는 엔티티 타입, 속성, 관계로 구성됩니다. SQL 쿼리는 데이터를 조회하는 방법일 뿐 온톨로지 정의 자체의 일부가 아닙니다.
```

```quiz
Q: 식별자 속성의 목적은 무엇인가요?
- 엔티티의 색상을 저장하기 위해
- 엔티티의 각 인스턴스를 유일하게 구분하기 위해 [correct]
- 두 엔티티를 서로 연결하기 위해
- 데이터 형식을 정의하기 위해
> 식별자 속성(예: 고객 ID)은 엔티티 타입 내에서 각 인스턴스를 유일하게 식별하여 시스템이 정확히 세고, 그룹화하고, 조인할 수 있게 합니다.
```
