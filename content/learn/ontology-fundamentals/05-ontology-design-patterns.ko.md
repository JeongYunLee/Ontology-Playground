## 사람이 읽는 이름으로 지어라

가장 중요한 설계 결정은 명명입니다. 엔티티 타입과 속성은 사람과 기계가 모두 읽습니다. 이름이 명확할수록 자연어 질의의 정확도도 올라갑니다.

**권장:**
- 엔티티 타입은 단수 명사로: `Customer`, `Product`, `Order`
- 속성은 camelCase로: `firstName`, `totalAmount`, `createdDate`
- 관계는 동사구로: `placedBy`, `worksAt`, `contains`

**지양:**
- 내부 테이블 이름 사용: `tbl_cust_v2`, `DIM_PRODUCT`
- 축약: `qty`, `amt`, `dt` — 풀어서 쓰세요
- 일반적인 이름: `Item`, `Record`, `Thing`

## 한 엔티티, 한 개념

각 엔티티 타입은 **하나의 비즈니스 개념**만 대표해야 합니다. 관계없는 속성을 계속 추가하고 있다면 아마도 엔티티를 분리해야 할 때입니다.

**안티패턴:** `Person` 엔티티에 `salary`, `patientId`, `courseGrade`, `accountBalance`를 모두 넣은 경우 — 이는 사실 네 개의 서로 다른 개념(Employee, Patient, Student, Customer)을 하나로 뭉쳐 놓은 것입니다.

**개선:** 별도 엔티티 타입을 만들고 필요할 때 연결하세요. `Person`은 `Employee` 레코드, `Patient` 레코드 등과 연결될 수 있습니다.

## 식별자를 신중히 고르세요

식별자 속성은 인스턴스가 어떻게 세어지고, 그룹화되고, 조인되는지 결정합니다. 좋은 식별자는 이렇습니다.

- 모든 인스턴스에 걸쳐 **유일함**
- **안정적** — 시간에 따라 바뀌지 않음
- **의미 있음** — 내부 자동 증가 값보다는 비즈니스 키 선호

예시: 책의 `isbn`, 사용자의 `email`, 주문의 `orderId`.

복합 식별자(여러 필드가 함께 키를 이루는 경우)는 피하세요. 대부분의 온톨로지 도구는 엔티티당 하나의 식별자를 기대합니다.

## 외래 키가 아니라 관계를 모델링하라

관계형 데이터베이스에서는 외래 키로 테이블을 연결합니다. 온톨로지에서는 명시적 의미를 가진 **이름 있는 관계**를 사용합니다.

| 관계형 | 온톨로지 |
|-----------|----------|
| `orders.customer_id → customers.id` | `Order` → `placedBy` → `Customer` |
| `order_items.product_id → products.id` | `OrderItem` → `contains` → `Product` |

관계 **이름**이 결정적입니다. 쿼리 엔진(과 사람)에게 연결이 무엇을 의미하는지 알려 주기 때문입니다. "placedBy"는 `fk_cust_id` 같은 컬럼 이름보다 훨씬 명확합니다.

## 카디널리티를 정확히 설정하세요

잘못된 카디널리티는 잘못된 집계를 낳습니다. 스스로 물어보세요. "A 하나에 대해 B는 몇 개까지 가능한가?"

- 고객 한 명이 **여러** 주문을 낼 수 있다 → one-to-many
- 주문 하나는 **한** 매장에서 처리된다 → many-to-one
- 학생 한 명이 **여러** 강의를 듣고, 강의 하나에 **여러** 학생이 등록한다 → many-to-many

## 흔한 실수를 피하세요

| 실수 | 문제 | 해결 |
|---------|---------|-----|
| **갓 엔티티(God entity)** | 하나의 엔티티에 30개 이상의 속성 | 초점이 명확한 엔티티들로 분리 |
| **식별자 누락** | 인스턴스를 셀 수도 그룹화할 수도 없음 | 유일한 식별자 속성 추가 |
| **모호한 관계 이름** | `relatedTo`, `hasLink` | 구체적 동사 사용: `prescribes`, `enrolledIn` |
| **순환 one-to-one** | A → B, B → A 둘 다 1:1 | 아마 같은 엔티티 — 합치세요 |
| **과잉 모델링** | 모든 내부 테이블이 엔티티가 됨 | 스키마가 아니라 사용자가 질의할 것만 모델링 |

## 설명은 언제 넣을까

모든 엔티티 타입, 속성, 관계는 선택적인 **설명**을 가질 수 있습니다. 아래와 같은 경우에 활용하세요.

- 이름만으로는 모호할 때 (`status`는 많은 뜻이 될 수 있음)
- 도메인 특화 개념일 때 (`formulary`, `SKU`, `yield`)
- 자연어 질의 해석에 힌트를 주고 싶을 때

## 핵심 정리

- 사람 기준으로 명명: 단수 명사, camelCase, 동사구
- 한 엔티티, 한 개념 — 과부하 상태의 엔티티는 분리
- 안정적이고 유일하며 의미 있는 식별자를 선택
- 외래 키 컬럼이 아니라 이름 있는 관계로 모델링
- 정확한 집계를 위해 카디널리티를 올바르게 설정
- 이름이 모호한 곳에는 설명을 추가

```quiz
Q: Person 엔티티에 salary, patientId, courseGrade, accountBalance 속성이 모두 들어 있습니다. 어떤 설계 패턴을 적용해야 할까요?
- 식별자 속성 추가
- 모든 속성을 하나의 설명 필드로 합치기
- 별도 엔티티 타입(Employee, Patient, Student, Customer)으로 분리하고 필요 시 관계로 연결 [correct]
- 하나만 남기고 나머지는 삭제
> 엔티티에 관련 없는 속성이 쌓이면 "갓 엔티티(god entity)"가 됩니다. 해결책은 각 개념을 별도의 엔티티 타입으로 나누고 필요할 때 관계로 연결하는 것입니다.
```
